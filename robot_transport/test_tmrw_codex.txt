I want you to replace my current ROS 2 ZeroMQ gateway with the simplest possible low-latency implementation for communication between a robot and a PC on the same Wi-Fi/LAN.

Environment:

* ROS 2 Humble
* RMW: CycloneDDS
* Robot and PC are on the same network
* Current transport is Python + pyzmq
* I already have a working ZeroMQ gateway, but it uses one REQ/REP connection per route
* I want to replace REQ/REP because I want minimum latency and no request/response synchronization
* I want one isolated ZeroMQ TCP connection per high-bandwidth stream
* Keep the code very small, readable, and easy to debug
* Do not build a generic middleware framework

First, inspect the ZeroMQ versions installed on the PC using:


Then give me the exact commands needed to install a compatible/same version on the robot. Prefer Ubuntu packages if versions are compatible. Do not force identical versions unless required by ZeroMQ compatibility.

The desired network architecture is:

```text
ROBOT ROS
   ↓
latest-sample slot
   ↓
compress
   ↓
ZeroMQ PUSH
   ↓
TCP/Wi-Fi
   ↓
ZeroMQ PULL
   ↓
decompress
   ↓
PC ROS
```

Do NOT use REQ/REP.

For continuous sensor streams use PUSH/PULL with:

* ZMQ_SNDHWM = 1
* ZMQ_RCVHWM = 1
* ZMQ_LINGER = 0
* no growing queues
* stale samples must be dropped
* newest data is more important than guaranteed delivery

Implement latest-sample semantics explicitly.

The ROS callback must never wait for compression or networking.

Desired behavior:

```text
ROS callback:
new message arrives
→ replace latest_message

worker:
take latest_message
→ encode once
→ send

if frames arrive while encoding:
discard older pending frames
→ process newest one next
```

Do not append sensor messages to a normal queue.

Also prevent ZeroMQ from accumulating stale packets. If PUSH/PULL cannot directly guarantee newest-only behavior, use non-blocking sends with HWM=1 and drop the sample when the socket cannot accept it. Do not block the producer waiting for the network.

Use one worker process per route as in the existing architecture so a large RGB/depth/pointcloud send cannot block `/scan` or another stream.

Compression requirements:

RGB:

* JPEG
* OpenCV
* quality around 80
* preserve ROS header
* decode back to normal `sensor_msgs/msg/Image` on the PC

Depth:

* initially keep lossless compression
* use Zstd level 1 unless `compressedDepth` is clearly simpler and better
* never convert depth to BGR or JPEG
* preserve original depth encoding such as `16UC1` or `32FC1`

LaserScan:

* ROS serialize using `rclpy.serialization.serialize_message`
* optionally Zstd level 1
* do not invent a custom LaserScan format

CameraInfo:

* serialize directly
* Zstd optional because it is tiny

PointCloud2:

* do NOT simply Zstd-compress raw PointCloud2 if Cloudini or ROS point-cloud transport is available
* install ROS 2 Humble point cloud transport tools/plugins first
* investigate/install:

  * `point_cloud_transport`
  * `point_cloud_transport_plugins`
  * Cloudini / `cloudini_ros`
* prefer Cloudini for PointCloud2 compression
* do not reimplement Cloudini
* use the existing ROS codec/converter or its codec API

Networking rules:

* bind only to the explicitly supplied robot/PC interface IP
* do not bind to `0.0.0.0`
* one TCP port per stream is fine
* one ZeroMQ context per process is fine
* each route runs in its own process
* TCP is acceptable
* use `ZMQ_IMMEDIATE` where useful
* `LINGER=0`
* keep HWM tiny
* sensor sender must never block because the receiver/network is slow
* drop instead of queue
* reconnect automatically after temporary network failures
* do not crash the entire gateway because one stream disconnects

Wire format:
Keep it minimal.

Use ZeroMQ multipart:

```text
part 0 = small JSON metadata
part 1 = payload bytes
```

Metadata only needs fields such as:

```json
{
  "version": 1,
  "sequence": 1234,
  "codec": "jpeg",
  "type": "sensor_msgs/msg/Image",
  "source_age": 0.012
}
```

Do not create a complicated protocol, CBOR framework, schema registry, heartbeat protocol, or RPC system.

For messages where ROS serialization already preserves header/frame/timestamps, do not duplicate all ROS metadata in JSON.

Stale data:

* store monotonic arrival time when the ROS callback receives the message
* if sample age exceeds `max_age`, do not send it
* after receiving on PC, discard samples that have obviously exceeded the configured age budget
* do not depend on synchronized PC/robot wall clocks
* sequence numbers should allow duplicate detection

Rate:

* `rate` is a maximum transmit rate
* if the source is slower, simply send source rate
* if the source is faster, sample the newest available frame at the configured maximum rate
* do not queue intermediate frames

For example, with camera 30 Hz and route rate 20 Hz:

```text
camera: 1 2 3 4 5 6 ...
sender: 1   3   5   ...
```

approximately, always preferring the newest available frame.

ROS QoS:
For these sensor topics use:

```text
BEST_EFFORT
KEEP_LAST
depth = 1
VOLATILE
```

Do not use RELIABLE for continuous RGB/depth/cloud unless there is a compelling reason.

The PC-side output must look like completely normal ROS 2 topics so downstream applications such as RViz, MoveIt, perception code, GraspGenX, etc. do not need to know ZeroMQ exists.
